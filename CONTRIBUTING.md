## Contributing Guidelines

### Team Development and Collaboration

For the development of PantryPlanner, our team uses GitHub to coordinate development,
manage changes, and keep track of individual contributions. Since multiple developers are
working on different parts of the application, we have established a consistent workflow that
allows everyone to contribute while also reducing the potential for conflicting changes.

Our general approach will involve working on separate branches, using pull requests to review
changes, and testing functionality before integrating it into the main project.
This allows us to work independently on different features while maintaining a shared and stable codebase.

## Development Workflow

### 1. **Branching**

Throughout the development process we use separate branches for individual features, bug fixes, and documentation
updates.
This allows each of the developers to work on their assigned tasks without directly affecting the main application.

**Examples of branch names:**

- feature/inventory-management
- fix/expiration-validation
- docs/project-setup

New branches are created from the most recent version on the main.

### 2. **Commits**

We aim to make smaller, focused commits that clearly describe the changes being made.
This makes it easier for team members to understand what was updated and allows us to track the development history.

**Examples:**

- feature: add inventory item model
- fix: correct expiration date validation
- docs: update project documentation
- test: add inventory API tests

### 3. **Pull Requests**

Once a developer completes a feature or update, the changes will then be pushed to GitHub and submitted through a pull
request.

Pull requests will provide the opportunity for other team members to review the implementation, ask questions,
and suggest improvements before the changes become part of the main application.

Each pull request should include a brief description of the change, as well as any relevant testing,
and reference to the associated GitHub issue where applicable.

### 4. **Code Review**

Our team aims to have at least one other developer review a pull request before it is merged.

This provides an opportunity to identify potential issues and make sure that changes are compatible with the rest of the
application.

### 5. **Testing**

When implementing new functionality or modifying existing features,
we aim to run the relevant tests and add new tests when needed.

### 6. **Merging and Synchronization**

After a pull request has been reviewed and the necessary changes, where needed, have been addressed
it will then be merged in the main branch.

## Project Coordination

GitHub Issues and the project backlog are used to organize development tasks,
track progress, and coordinate responsibilities between our team.

This approach will help us to maintain visibility into the overall development process
while allowing our individual team members to focus on their assigned areas of the application.
